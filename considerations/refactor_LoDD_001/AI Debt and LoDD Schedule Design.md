# AI負債とLoDDのスケジュール設計

## 「AI負債」の定義

まず用語を明確にします。技術的負債のAI版ですが、性質が異なります。

### 従来の技術的負債

```
「正しいやり方」を知っているが、時間がないので妥協する
→ 負債の内容が明確 → 返済方法も明確
```

### AI負債

```
AIが生成したコードの「何が妥協されているか」が不明
→ 負債の内容が不透明 → 返済コストが読めない
```

これが本質的な違いです。人間が意図的に積む負債は管理可能ですが、AIが無自覚に積む負債は**存在すら検知しにくい**。

### AI負債の具体的な内訳

| 負債の種類 | 内容 | 潜伏期間 |
|-----------|------|---------|
| **理解負債** | AIが生成したコードを、人間が十分に理解していない | 変更が必要になるまで潜伏 |
| **契約負債** | interfaces/ に書かれていない暗黙の契約がコードに埋まっている | 別モジュールとの結合時に発覚 |
| **環境負債** | 特定のDCCバージョンでしか動かない前提がハードコードされている | DCC更新時に発覚 |
| **テスト負債** | Done条件を満たすが、エッジケースが検証されていない | 本番データ投入時に発覚 |
| **知識負債** | knowledge/ に転記すべき知見が iterations/ に埋もれたまま消えている | 次のプロジェクトで同じ地雷を踏む |

---

## LoDDはAI負債に対してどう機能しているか

現行のLoDDは、すでにいくつかの負債を構造的に抑制しています。

| 負債の種類 | LoDDの対策 | 効果 |
|-----------|-----------|------|
| 理解負債 | Context Boundaryで範囲限定 → 人間がレビューすべき範囲が小さい | **抑制** |
| 契約負債 | interfaces/ で契約を明示 | **抑制** |
| 環境負債 | knowledge/ でDCC固有の注意点を蓄積 | **部分的に抑制** |
| テスト負債 | Done条件の type 分類 | **検知の仕組みはあるが、カバレッジは人間依存** |
| 知識負債 | iterations/ → knowledge/ の転記ルール | **ルールはあるが強制力がない** |

つまり、LoDDは**負債の発生を抑制する設計**にはなっていますが、**発生した負債をいつ・どう返済するか**のスケジュール設計が欠落しています。

## 返済時期の設計 — 3つの選択肢

### 選択肢A: タスク完了時に都度返済

```
Task実行 → Done → 即座にレビュー・返済 → 次のTask
```

**利点:** 負債が蓄積しない。問題が小さいうちに潰せる。

**欠点:** 各タスクのリードタイムが伸びる。数日〜10日のサイクルで毎回これをやると、**実装に使える時間が圧迫される**。LoDDの Retrospective の3行記録はこの方式に近いが、記録だけでは返済にならない。

### 選択肢B: Phase完了時にまとめて返済

```
Task-1 → Task-2 → Task-3 → Phase完了 → まとめてレビュー・返済
```

**利点:** 実装フェーズの速度を犠牲にしない。返済のまとまりがあるので効率的。

**欠点:** Phase完了まで負債が蓄積する。発見が遅れるほど修正コストが増大する。

### 選択肢C: サイクル末尾に返済スプリントを設ける

```
[実装サイクル: 7日] → [返済スプリント: 1〜2日] → 次のサイクル
```

**利点:** 実装と返済が明確に分離される。返済の時間が「予算化」されるので省略されにくい。

**欠点:** 返済スプリントで何をすべきかの基準が必要。

---

## 現実的な解: C の変形 — 「返済をサイクルに組み込む」

想定スケール（数日〜10日サイクル）に照らすと、**選択肢Cをベースに、AとBの要素を組み合わせる**のが現実的です。

### サイクル構造

```
数日〜10日のサイクル:

Day 1        : 設計・タスク分解（Phase構造なら specification.md）
Day 2〜N-2   : 実装（タスク実行）
Day N-1      : 返済スプリント ← ここを確保する
Day N        : 納品・デプロイ・振り返り
```

**返済スプリントに最低1日を確保する。** これは「余裕があればやる」ではなく、**サイクルの構造として最初から組み込む**ことが重要です。

### 実装中の軽量返済（選択肢Aの要素）

全てを返済スプリントまで先送りするのではなく、各タスク完了時に**5分でできる最小限の返済**は都度行います。

```markdown
## タスク完了時チェック（5分以内）
- [ ] Retrospective の3値を記入した
- [ ] iterations/ に knowledge/ に転記すべき内容がないか確認した
- [ ] 自分がAI生成コードの各関数の意図を1行で説明できるか確認した
      → 説明できない関数があれば、返済スプリントの対象としてマークする
```

3つ目が**理解負債の検知**です。「このコード何してるか分からないけど動いてる」を放置しない。

## 返済スプリントで何をするか

### 返済アクションの定義

| ID | 返済アクション | 対象負債 | 所要時間目安 |
|----|--------------|---------|-------------|
| R-001 | AI生成コードの通読・コメント追記 | 理解負債 | 30分〜1時間 |
| R-002 | interfaces/ と実装の突き合わせ | 契約負債 | 15分/モジュール |
| R-003 | エッジケーステストの追加 | テスト負債 | 30分〜1時間 |
| R-004 | knowledge/ への転記（未実施分） | 知識負債 | 15分/件 |
| R-005 | DCC バージョン依存箇所の洗い出し | 環境負債 | 30分 |
| R-006 | Retrospective の集計・傾向分析 | メタ判断 | 15分 |

### 優先順位の判断基準

全てを1日で返済する必要はありません。優先順位は**「次のサイクルで踏む確率」**で決めます。

```
高: 次のサイクルで確実に触るモジュールの理解負債・契約負債
中: 本番データ投入前に検証すべきテスト負債
低: 当面触らないモジュールの環境負債
```

## LoDDへの構造的な組み込み

### タスク定義への追加

```markdown
## Debt Markers（タスク完了時に記入）
- unreviewed_functions: []    # 意図を説明できない関数名のリスト
- untested_edges: []          # 検証していないエッジケースのリスト  
- implicit_assumptions: []    # interfaces/ に書かれていない暗黙の前提
```

これは Retrospective と並列する**負債の可視化セクション**です。返済スプリントで何をすべきかが、ここから自動的に導出されます。

### Phase構造での返済管理

Phase構造では、`work_log.md` に返済の実施記録を残します。

```markdown
## 2026-03-08: 返済スプリント

### 実施した返済
- R-001: mesh.py の三角形分割ロジックを通読。コメント追記済み
- R-002: interfaces/mesh_data.md と mesh.py を突き合わせ。
         法線の正規化が保証されていない箇所を発見 → テスト追加
- R-004: dcc_maya_skincluster.md を knowledge/ に転記

### 残存負債（次サイクルに繰り越し）
- R-003: material処理のエッジケーステスト（優先度:中）
- R-005: Houdini 20.5 での動作未確認（優先度:低）
```

## 「返済しない」という判断もある

全ての負債を返済すべきとは限りません。

```
このツールは今回のショット作業専用で、二度と使わない
→ 理解負債もテスト負債も返済不要。動けばいい。
```

```
パイプラインの標準ツールとして長期運用する
→ 全負債を返済すべき。特に理解負債と環境負債。
```

**ツールの寿命が返済の判断基準**です。LoDDのサイクル設計に、**「このツールの想定寿命」**を明記する欄があると、返済の要否が明確になります。

```markdown
# architecture.md に追記

## Tool Lifecycle
- expected_lifespan: single-shot | short-term (<3months) | long-term
- debt_policy:
  - single-shot: 返済不要。動作すれば完了
  - short-term: 理解負債・契約負債のみ返済
  - long-term: 全負債を返済。knowledge/ への転記を必須化
```

## まとめ: スケジュール観の全体像

```
サイクル開始
  │
  ├─ architecture.md に Tool Lifecycle を明記
  │  → 返済ポリシーが決まる
  │
  ├─ 実装フェーズ（Day 2〜N-2）
  │    各タスク完了時:
  │    ├─ Retrospective（3値記録: 5分）
  │    ├─ Debt Markers（負債の可視化: 5分）
  │    └─ iterations/ → knowledge/ 転記の確認
  │
  ├─ 返済スプリント（Day N-1）← 構造として確保
  │    ├─ Debt Markers から返済対象を抽出
  │    ├─ Tool Lifecycle に応じて優先順位付け
  │    └─ 実施記録を work_log.md に残す
  │
  └─ 納品・振り返り（Day N）
       └─ Retrospective 集計 → 次サイクルの改善
```

結局のところ、AI負債の問題は**「返済すべきかどうか」の判断基準**と**「返済する時間を構造的に確保する」**の2点に帰着します。前者は Tool Lifecycle で、後者は返済スプリントのサイクル組み込みで解決できます。どちらもLoDDの既存構造に自然に接続可能で、設計思想を変更する必要はありません。
