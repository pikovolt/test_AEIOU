## 2. 再検討の趣旨

この階層での再検討の趣旨は **「正本（v1.1）が2つの議題をどれだけカバーできているか」** を精査することである。

具体的には以下の点を確認する:

- 議題・その１（セマンティックドリフト）の論点・対策が v1.1 にどの程度正確に統合されているか
- 議題・その２（AI負債とスケジュール設計）の論点・推奨案が v1.1 にどの程度正確に統合されているか
- 統合の過程で脱落・変質・矛盾が生じている箇所はないか
- v1.1 単体で議題の結論を追跡できるか、元文書の併読が必要な箇所はどこか

## 3. 検出済みの検討ポイント — 議題・その１: セマンティックドリフト

**S-1: 防壁テーブルの実現手段が不正確**
v1.1 の6つの防壁テーブルで、6番目「AI負債の可視化」の実現手段が `Debt Markers + 返済スプリント` とある。これはAI負債管理の手段であり、セマンティックドリフト検知の手段ではない。元文書では `Contract Test + Merge Gate` と明記されている。防壁テーブルにセマンティックドリフトが含まれていないか、混同が起きている。

**S-2: 「5つの防壁」から「6つの防壁」への拡張の妥当性**
元文書の結論は「現行スケールでは直列のまま運用すべき」。にもかかわらず v1.1 で6番目の防壁として格上げされている。参考セクション（拡張パス）に留めた方が、「今は不要」という判断と整合するのではないか。

**S-3: 元文書の位置付け**
v1.1 に統合済みの場合、元文書は「議論経緯のアーカイブ」なのか「v1.1 と並行して参照すべき詳細資料」なのかが不明。SSOTの原則からすると正本は v1.1 のみとし、元文書はアーカイブ扱いが妥当だが、明示されていない。

**S-4: Contract Test の位置付けの曖昧さ**
v1.1 の拡張パスでは `tests/contracts/` を新設するとあるが、元文書では Contract Test の詳細（テストコード例、配置構造、テスト種別テーブル）が記載されている。この詳細情報が v1.1 に圧縮された際に落ちている。拡張パスを実際に着手する際に元文書を参照しないと実装判断ができない。

## 4. 検出済みの検討ポイント — 議題・その２: AI負債とスケジュール設計

**D-1: 選択肢A/B/Cの議論経緯が v1.1 から脱落**
元文書は3つの返済タイミング選択肢を比較評価し「Cの変形」を推奨している。v1.1 では結論（返済スプリントのサイクル組み込み）のみ記載。なぜこの方式を選んだかの根拠が v1.1 単体では追えない。

**D-2: 「返済しない」という判断の扱い**
元文書は「ツールの寿命が返済の判断基準」として `single-shot` なら返済不要と明記。v1.1 では Tool Lifecycle の `debt_policy` に反映されている。しかし損益分岐点テーブルと debt_policy の関係が暗黙的。single-shot なら LoDD が過剰 → そもそも LoDD を使わない → debt_policy が参照されない、という循環がある。

**D-3: タスク完了時の「5分チェック」の実現可能性**
元文書・v1.1 ともに「AI生成コードの各関数の意図を1行で説明できるか確認」を5分以内としている。500行×十数モジュール規模で、1タスクあたりの変更範囲が3〜5ファイルの場合、5分は過小ではないか。特に理解負債の検知は読解を伴うため、見積もりの根拠が不明。

**D-4: 元文書の「サイクル全体像」図と v1.1 の「サイクル全体」図の微差**
元文書では `architecture.md に Tool Lifecycle を明記` がサイクル開始直後。v1.1 では同じだが、元文書にあった `iterations/ → knowledge/ 転記の確認` が実装フェーズのタスク完了時チェックとして記載。意味は同じだが粒度が微妙に異なっており、参照時に混乱の元になる。
