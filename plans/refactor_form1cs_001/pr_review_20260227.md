# PRレビュー所見（2026-02-27）

## 対象
- PR #3〜#8 相当の履歴（plan/worklog更新と先行リファクタ実装）

## 結論（先に要点）
- 「異常にスムーズ」というより、**段階設計 + 小PR + 早期修正が機能しているため、見た目がスムーズ**という評価が妥当。
- 一方で、現時点の進捗は **Aフェーズ（先行分離）中心**で、難所であるモデル分離/VirtualMode は未着手領域が多い。
- したがって、違和感は合理的であり、今後（Phase 1以降）で難易度が上がる可能性を前提に管理するべき。

## 根拠（履歴から見えること）

### 1) 実装は「いきなり本丸」ではなく、先行分離に限定
- 計画上、A-1〜A-5（選択・スクロール・描画委譲）を完了としており、モデル分離（Phase 1）は未完了のまま。
- worklogでも「既存動作を変えないロジック抽出＋委譲」を優先した記録になっている。

### 2) 問題は実際に発生しており、修正も入っている
- Enter移動時の選択クリア責務ズレを検出し、呼び出し側責務へ戻す修正が明記されている。
- さらにアクセシビリティ修正（公開範囲の整合）も後続PRで入っており、完全にノートラブルではない。

### 3) 計画運用は一度揺れて戻している
- plan_002を作ってから plan_001 を正に戻す履歴があり、計画運用は試行錯誤している。
- 「常に一直線」ではなく、ドキュメント運用の見直しが発生している。

## 一般論としての妥当性
- この進め方（小PR・責務抽出先行・回帰時は即修正）は、一般に**失敗確率を下げる定石**。
- そのため「見た目が順調」自体は不自然ではない。
- ただし、最難関は通常この後（データモデル化、Undo/Redo整合、VirtualMode接続、性能保証）に出る。

## 違和感への回答（実務的な見方）
- 違和感の正体は、
  - 進捗ログが整っていて成功が強調されやすいこと、
  - まだ高リスク領域（Phase 1以降）に本格突入していないこと
  の2点で説明できる。
- よって「不自然な成功」より「**難所前の準備フェーズが上手く回っている状態**」と解釈するのが妥当。

## 次フェーズでの監視ポイント（推奨）
1. `dataGridView[col,row].Value` 直参照の残件数を定量化（毎PRで差分報告）
2. Undo/Redo の操作単位互換（SetValueOperation）を回帰観点として固定
3. VirtualMode準備として `CellValueNeeded/CellValuePushed` への接続可否を早期にスパイク
4. P95 25ms 指標は「測定手順」も先に固定して、主観評価を排除

## 追加: 危険な兆候（先行列挙）

### A. 設計・責務境界の兆候
1. `TimingSheetModel` に UI都合（選択状態、スクロール位置、色判定）が混入し始める
2. 逆に `Form1` がモデル更新の詳細知識を持ち続け、二重責務が固定化する
3. 新規サービスクラスが増える一方で `Form1` 行数/分岐が減らず、実質移管できていない
4. 「とりあえず adapter で吸収」が恒常化し、暫定層が本番責務になる

### B. 実装進行の兆候
5. `dataGridView[col,row].Value` 直参照の残件数が減らない、または減少ペースが鈍化する
6. PRごとの変更量が急増し、1PRで入力/描画/モデルを同時に触るようになる
7. 仕様差分の説明が「挙動は同じ想定」に留まり、根拠テストや検証手順が添付されない
8. リグレッション修正PRが連鎖し、根本設計ではなく後追いパッチ中心になる

### C. Undo/Redo・データ整合の兆候
9. Undo/Redo で old/new 値の取得元が混在し、再現不能バグが出始める
10. 複数セル更新（連番/置換/四則演算）で操作単位が揺れ、Undo 1回で戻る範囲が変動する
11. モデル更新と画面反映のタイミングがズレ、見た目と実データの不一致が発生する
12. 保存/読込経路がモデル経由と UI経由で分岐し、同一データでも結果が異なる

### D. VirtualMode移行の兆候
13. `CellValueNeeded` で O(1) 取得を守れず、イベント内で探索や変換を繰り返す
14. `CellValuePushed` と既存入力経路の責務分担が曖昧で、更新経路が二重化する
15. 行列サイズ同期の基点が統一されず、表示範囲外アクセスや Index エラーが増える
16. VirtualMode ON/OFF で挙動差が顕在化するのに、互換条件が文書化されない

### E. 性能・品質保証の兆候
17. P95 25ms 目標に対し、測定条件（データサイズ、操作シナリオ、採取回数）が固定されない
18. 「体感で速い/遅い」評価に戻り、PR単位の客観比較ができなくなる
19. 手動スモーク観点（入力/移動/選択/Undo/Redo/保存読込）が欠落し、回帰検知が遅れる
20. 失敗時のロールバック方針（どの単位で戻すか）がなく、問題発生時に復元コストが高騰する

## 危険兆候を早期検知するための運用提案
- 兆候トラッキング表を作り、各PRで「該当あり/なし + 根拠」を必須記載にする
- Phase 1/2 は「完了率」より「直参照残件」「Undo回帰件数」「P95差分」を主要KPIに置く
- 週次で「計画逸脱レビュー」を実施し、逸脱時は decision_log に理由・是正案・期限を残す
- スパイク実装（VirtualMode接続検証）は本流PRと分離し、学習結果のみを本流へ還元する

## 総評
- 現時点のPR群は、一般的に見て「順調すぎて危険」というより、
  **段階分割とリスク隔離が効いている良い進行**。
- ただし本当の評価は Phase 1〜2（モデル分離〜VirtualMode）で決まるため、
  ここからは進捗より「回帰率・性能計測・設計逸脱」の監視を強めるべき。
- 上記20項目の危険兆候を先行管理することで、違和感を「不安」ではなく「観測可能なリスク」に変換できる。
